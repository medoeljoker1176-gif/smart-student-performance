# Model Card — Smart Student Performance AI

## Summary
This is a university learning prototype that estimates whether a record belongs to the synthetic `Pass` or `Fail` class. It is an educational demonstration, not a validated student assessment product.

## Intended use
- Demonstrate a supervised classification workflow, preprocessing pipelines, model comparison, model explanations, and dashboard reporting.
- Support a classroom project discussion about early-warning system design.
- Explore hypothetical student profiles using generated data.

## Datasets
The default dataset is synthetic. An optional second model is trained on the real UCI Student Performance data (one pair of Portuguese schools, 2005-2006). It is selected in the sidebar and has separate metrics. Its accuracy is high mainly because earlier grades (G1, G2) predict the final grade (G3); it does not show the model would work in other schools or countries.

## Access control
When login is enabled, teachers see every page and students only Prediction, AI Explanation, Recommendations and About. Student records, batch uploads and history are teacher-only.

## Out-of-scope use
- Official grades, admission, scholarship, discipline, or other consequential decisions.
- Diagnosing student ability or motivation.
- Generalizing results to real schools, universities, or demographic groups.
- Automatically deciding that a student will fail or does not deserve an opportunity.

## Data
The included dataset is generated locally by `generate_dataset.py` with a fixed random seed. It contains 1,000 synthetic rows and 10 input features plus `Result`. Features are generated from hidden traits (ability, discipline, background) so they correlate realistically, and the target comes from a hidden exam score (not saved, to avoid leakage) plus noise; it is not an independently observed real-world outcome. Some feature values are intentionally missing to demonstrate imputation.

Because the label-generating rule and model inputs share related variables, reported metrics show how well the model learns this synthetic process. They are not evidence of performance on real students.

## Model and evaluation
The training workflow compares Logistic Regression, Decision Tree, Random Forest, and Gradient Boosting. Preprocessing is inside each scikit-learn pipeline. The data is split before learned preprocessing is fitted; model selection uses stratified cross-validation on the training split, and the held-out test split is reserved for final metrics. The selected artifact and metrics are saved locally.

Read the current `reports/metrics.json` for results generated by the current training run. Do not copy results from older runs without regenerating and checking them. Small differences among models on a 200-row test set should not be over-interpreted.

## Outputs
- Predicted label (`Pass` or `Fail`).
- Estimated probability of `Pass`.
- Prototype risk tier based on configured probability thresholds.
- Exact Shapley-style feature contributions for model interpretation.
- Rule-based educational suggestions and hypothetical model responses.

Risk thresholds are design choices, not validated cut-offs. Explanation values describe model behavior and do not prove causation. What-if outputs are hypothetical model responses, not evidence that changing a behavior will cause a particular result.

## Fairness and privacy
The repository includes a basic group comparison using synthetic `Gender` values and out-of-fold predictions. This cannot prove fairness and should not be generalized to real people. A real deployment would require lawful data collection, consent, privacy controls, broader fairness analysis, independent validation, monitoring, and human oversight.

Prediction history is stored locally in `data/prediction_history.csv` when the user saves a prediction. Use anonymous identifiers for demos, avoid real personal data, and clear the history when finished. This prototype does not provide production-grade authentication or multi-user access control.

## Known limitations
- Synthetic data only; no real-world validation.
- Small dataset and held-out test set.
- Fixed features and a binary target.
- Risk thresholds are heuristic.
- Fairness checks cover limited groups and metrics.
- Local CSV history is not a secure multi-user database.
- Application UI must be tested in an environment with the dependencies installed.

## Responsible use
Use predictions only as prompts for supportive human review. Do not use this prototype as the sole basis for any consequential decision about a student.
